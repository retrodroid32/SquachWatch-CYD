# v1.20.1 history reconciliation

This file records the changelog audit performed before the v1.20.1 release.

## Scope

- Baseline tag: `v1.20.0`
- Baseline commit: `95edaffad7eddb8543b03e5f045fbfe1fff26653`
- Reconciliation source head: `cc8da572fc05a99a81eee789fbbe61f8ae40238b`

The audit used the complete Git comparison from v1.20.0 to the source head, not
only recent conversation context or the latest commit subjects.

  web-flasher exposure, release artifacts and CI coverage.

  RADIO RESET, deep-sleep recovery, STEADY POWER, temperature/hearing

  host-test compatibility.

- OTA allocation/TLS/version handling and fork-facing update URLs.
- Board/release matrix validation, dependency pinning and public board support.
- Production Pages/release separation, lab-site preservation, exact-artifact
  publishing, signing validation and least-privilege workflow permissions.
- Stage 1 performance queue budgeting and frame/queue telemetry.

## Superseded intermediate commits

A historical changelog should describe what the release actually does, not
every temporary implementation on the way there. Where a later commit replaced
an earlier approach, the final behavior is documented.

Examples:

- A temporary workflow that published the web flasher from ordinary `master`
  was later replaced. v1.20.1 documents the final rule: production Pages is
  deployed only from the validated release/lab `pages-site` artifact.
- Early T-Watch radio recovery used an AXP2101/PMU restart. That was replaced
  after hardware testing by a one-second deep-sleep restart, which is the
  behavior documented for v1.20.1.
- Several upstream-sync commits merely moved declarations/files into parity.
  Their resulting user-visible behavior is recorded once rather than repeated
  as separate release-note bullets.

## Maintenance rule

For the rest of v1.20.1 development, any change that affects user-visible
behavior, hardware support, detection behavior, reliability, security,
performance, diagnostics, installation, OTA, release publishing or known
limitations should update the active release notes in the same change set.
README updates are required when the change alters current setup, supported
hardware, major capabilities or operator-facing diagnostics.
